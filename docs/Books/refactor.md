# 序言

重构（refactoring）：在不改变代码外在行为的前提下，对代码作出修改，以改进程序的内部结构，是一种经千锤百炼形成的有条不紊的**程序整理方法**，可以最大限度地减小整理过程中引入错误的概率。

如果一段代码能正常工作，并且不会再被修改，那么完全可以不去重构它。能改进之当然很好，但若没人需要去理解它，它就不会真正妨碍什么。如果确实有人需要理解它的工作原理，并且觉得理解起来很费劲，那你就需要改进一下代码了。

- 要求：可靠的具有自我检验的测试。
- 精髓：小步修改、每次修改后就运行测试。

好代码的检验标准就是人们能否轻而易举地修改它。

# 重构的原则

### 重构的定义

​	重构（名词）：对软件内部结构的一种调整，目的是在不改变软件可观察行为的前提下，提高其可理解性，降低其修改成本。

​	重构（动词）：使用一系列重构手法，在不改变软件可观察行为的前提下，调整其结构。

### 重构与性能优化的区别

重构是为了让代码更容易理解和修改，可能使程序运行得更快，也可能更慢。

性能优化只关心程序运行得更快，最终得到的代码可能更难理解和维护。

# 代码的坏味道

每当感觉需要以注释来说明点什么的时候，我们就把需要说明的东西写进一个独立函数中，并以其用途（而非实现手法）命名。我们可以对一组甚至短短一行代码做这件事。哪怕替换后的函数调用动作比函数自身还长，只要函数名称能够解释其用途，我们也该毫不犹豫地那么做。关键不在于函数的长度，而在于函数“做什么”和“如何做”之间的语义距离。

# 封装

使用封装的方法分解模块，隐藏一个记录/集合不需要被外界关心的信息，将它们封装成类，对属性的操作通过方法访问，保持数据的不可变性，能够让对记录/集合的每一项改动都能被程序员所跟踪，避免数据的污染。

# 搬移特性

**命令查询分离原则**：

- **查询：**方法返回结果，但不改变任何系统状态(无副作用)。
- **命令：**方法没有结果，但会改变系统状态。

在设计时，应将两种状态分开，避免在同一方法中既有查询又有命令。

**优点：**

1. 查询类型的方法，对于调用者来讲不用在顾虑各个查询方法的调用顺序和次数(忽略性能的因素)。
2. 命名类型的方法，从语义上来讲更准确。
3. 直观地判断一个函数是否产生副作用。

# 重新组织数据

## 拆分变量

移除对变量的赋值。

如果一个变量被赋值超过一次，意味着它们在函数中承担了一个以上的责任。该变量就应该被拆分为多个变量，每个变量只承担一个责任。

## 字段改名

随着开发的进展，字段的命名很难在一开始就能涵盖其所有职责，因此需要逐步地对字段改名，使其在每个阶段都有最恰当的意义

## 以查询取代派生变量

若有些变量可以通过其他变量计算出来，那么可以去掉这个变量，改用函数返回值的方式，每次访问这个变量改为获取该函数计算的返回值。（函数提炼）

可变数据是软件中最大的错误源头之一，在软件开发中，应当尽可能把可变数据的作用域限制在最小范围。

## 将引用对象改为值对象

值对象与引用对象的区别：值对象是不可变的。

在把一个对象嵌入另一个对象时，可以将位于内部的对象视为对象，更新其属性时，替换整个内部对象，这样可以不必担心对象中的包装的数据被偷偷修改，也不必操心维护内存的链接。

## 将值对象改为引用对象

一个数据结构中可能包含多个记录，而这些记录都关联到同一个逻辑数据结构。如果将该逻辑结构视为值对象，那么这多个记录都会复制该逻辑结构的数据。若视为引用对象，就只有一份数据结构。这样做易于对这个对象的更新。

把值对象改为引用对象会带来一个结果：对于一个客观实体，只有一个代表它的对象。可以定义一个仓库，在仓库中可以找到所有这些实体对象。只为每个实体创建一次对象，以后始终从仓库中获取该对象

# 简化条件逻辑

程序的复杂度大多来自条件逻辑，可以通过分解/合并条件表达式理清逻辑集合。

## 分解条件表达式

将繁琐的条件表达式进行拆解，并使用提炼函数的手法把具有相同特质/职责的判断提炼为函数。

## 合并条件表达式

对于多个条件检查但执行行为一致的逻辑判断，可以使用逻辑运算，将它们合并成一个条件表达式。

## 以卫语句取代嵌套条件表达式

如果某个条件极其罕见，对这个条件进行单独检查，并在该条件为真时立刻从函数中返回，这样的单独检查常被称为“卫语句”。

将嵌套条件表达式拆离开来，对于具有特殊行为，如返回空值等非函数主体执行工作的，可以使用卫语句，提前返回，使嵌套条件表达式的可读性更好。

## 以多态取代条件表达式

对于switch...case语句，如果涉及到一组类型的不同处理逻辑的判断，可以为这一组类型创建一个公共父类（抽象类），并实现各个类型的多态，运用多态的特性执行对应类型的行为，这种做法比条件表达式有更好的可读性和可维护性。

## 引入特例

对于空对象，或某个特殊值处理的判断，并且该特殊值出现时所作的处理也相同，则可以为这个特殊值创建一个特例元素，用以表达对这种特例的共用行为的处理，并用一个函数调用取代大部分特例检查逻辑。

## 引入断言

当某段代码只有某个条件为真时才能正常运行时，可以引入断言表达式。将断言设计在设值函数处，可以清晰地看到非法值是在何处被设置的。

# 重构API

模块和函数是软件的骨肉，而 API 则是将骨肉连接起来的关节。

## 将查询函数和修改函数分离

任何有返回值的函数，都不应该有**看得到的副作用**——命令与查询分离。

看不到的副作用：将查询所得结果缓存于某个字段中，这样一来后续的重复查询就可以大大加快速度。虽然这种做法改变了对象中缓存的状态，但这一修改是察觉不到的，因为不论如何查询，总是获得相同结果。

## 函数参数化

如果两个函数逻辑非常相似，只有一些字面量值不同，可以将其合并成一个函数，以参数的形式传入不同的值，从而消除重复。

## 移除标记参数

“标记参数”是这样的一种参数：调用者用它来指示被调函数应该执行哪一部分逻辑。

```plain
bookConcert(aCustomer, CustomerType.PREMIUM);
```

如果调用者传入的是程序中流动的数据，这样的参数不算标记参数；只有调用者直接传入字面量值，这才是标记参数。

**做法**：针对参数的每一种可能值，新建一个明确函数。

但在下面这种情况下，很难将isRush的分发逻辑剥离到顶层。

```javascript
function deliveryDate(anOrder, isRush) {
  let result;
  let deliveryTime;
  if (anOrder.deliveryState === "MA" || anOrder.deliveryState === "CT")
    deliveryTime = isRush? 1 : 2;
  else if (anOrder.deliveryState === "NY" || anOrder.deliveryState === "NH") {
    deliveryTime = 2;
    if (anOrder.deliveryState === "NH" &amp;&amp; !isRush)
    deliveryTime = 3;
  }
  else if (isRush)
    deliveryTime = 3;
  else if (anOrder.deliveryState === "ME")
    deliveryTime = 3;
  else
    deliveryTime = 4;
  result = anOrder.placedOn.plusDays(2 + deliveryTime);
  if (isRush) result = result.minusDays(1);
  return result;
}
```

可以退而求其次，在这个函数之上再添加两个函数，分别代表这个函数的一部分使用方式。

```javascript
function rushDeliveryDate(anOrder) {
  return deliveryDate(anOrder, true);
}
function regularDeliveryDate(anOrder) {
  return deliveryDate(anOrder, false);
}
```

## 保持对象完整

“传递整个记录”的方式能更好地应对变化：如果将来被调的函数需要从记录中导出更多的数据，我就不用为此修改参数列表。并且传递整个记录也能缩短参数列表，让函数调用更容易看懂。

从一个对象中抽取出几个值，单独对这几个值做某些逻辑操作，这是一种代码坏味道（依恋情结），通常标志着这段逻辑应该被搬移到对象中。

```java
const low = aRoom.daysTempRange.low;
const high = aRoom.daysTempRange.high;
if (!aPlan.withinRange(low, high))
    alerts.push("room temperature went outside range");
```

重构为

```javascript
const tempRange = aRoom.daysTempRange;
const isWithinRange = aPlan.xxNEWwithinRange(tempRange);
if (!isWithinRange) alerts.push("room temperature went outside range");
//class HeatingPlan...
xxNEWwithinRange(tempRange) {
  const low = tempRange.low;
  const high = tempRange.high;
  const isWithinRange = this.withinRange(low, high);
  return isWithinRange;
}
```

## 以查询取代参数

函数的参数列表应该总结该函数的可变性，标示出函数可能体现出行为差异的主要方式。和任何代码中的语句一样，参数列表应该尽量避免重复，并且参数列表越短就越容易理解。

重复的参数：如果调用函数时传入了一个值，而**这个值由函数自己来获得也是同样容易**，这就是重复。

不使用以查询取代参数最常见的原因：移除参数可能会给函数体增加不必要的依赖关系——迫使函数访问某个程序元素，不需要新增这种“不必要的依赖关系”。

## 以参数取代查询

权衡关系：如果把所有依赖关系都变成参数，会导致参数列表冗长重复；如果作用域之间的共享太多，又会导致函数间依赖过度。

对于上一种重构方式，如果查询中出现了“不必要的依赖关系”，则可以使用该重构方式解决这种问题。

**引用透明性**

如果一个函数用同样的参数调用总是给出同样的结果，我们就说这个函数具有“引用透明性”（referential transparency），这样的函数理解起来更容易。

如果一个函数使用了另一个元素，而后者不具引用透明性，那么包含该元素的函数也就失去了引用透明性。

只要把“不具引用透明性的元素”变成参数传入，函数就能重获引用透明性。
